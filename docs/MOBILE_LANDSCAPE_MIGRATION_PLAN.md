# 小遊戲手機橫向版面遷移計劃書

- 文件日期：2026-09-03
- 專案階段：維護／正式介面遷移
- 主要使用情境：手機橫向
- 目標最低視窗：640 × 360
- 主要設計基準：844 × 390
- 大型手機驗證：932 × 430

## 1. 計畫目的

### Acceptance 路徑政策

本計畫的完成條件是每款遊戲通過手機橫向標準，不是最大化共用元件使用率。依實機證據，遊戲可採 `KEEP`、`LIGHT` 或 `FULL`：現有結構已符合標準則 KEEP；核心結構正確但需小幅 responsive／accessibility／共用控制修正則 LIGHT；只有主要互動在 640×360 無法合理共存時才採 FULL。這項政策不改變既有完成數；本輪七款剩餘 BOARD 遊戲僅完成 audit，維持 35/59。

隨著小遊戲數量增加，逐款獨立調整已造成頁首、操作區、回饋方式、觸控尺寸與橫向高度利用不一致。本計畫的目標是建立可重複使用的版面規格，逐批遷移 59 款現有遊戲，並讓未來新增遊戲能直接套用同一套分類、元資料、版型與驗收方式。

玩家端預期結果：

- 在手機橫向畫面中，不需捲動整個頁面即可理解目標並完成主要操作。
- 返回、說明、重設、作答與下一步等操作位置一致且容易點擊。
- 題目、盤面、選項、狀態與回饋具有穩定的視覺層級。
- 一般與進階難度的首頁說明、遊戲內容及規則文字一致。
- 新遊戲能依內容類型選擇既有版型，不再從零個別設計。

## 2. 計畫範圍與非目標

### 本計畫包含

- 59 款遊戲的版面分類與遷移。
- 共用頁面骨架、版面元件與響應式規格。
- 手機橫向的文字可讀性、觸控尺寸、狀態回饋與安全區。
- 一般／進階模式的標示與說明一致性。
- 契約測試、正式版建置與代表尺寸瀏覽器實測。
- 遷移進度、風險與交接文件。

### 本計畫不包含

- 全面重寫遊戲規則或計分機制；只有發現明確錯誤時才另案處理。
- 美術資產全面重製。
- 後端、帳號、雲端同步或多人連線功能。
- 在版面遷移批次中同時處理大型效能重構。
- 為了消除局部溢位而任意縮小文字。

## 3. 已建立的統一規格

### 3.1 單一遊戲目錄

`data/gameCatalog.ts` 已收錄 59/59 款遊戲，統一管理：

- 遊戲名稱
- 五種內容分類
- 一般／進階說明
- 能力標籤
- 遊玩方式
- 版面預設

目錄完整性由 `tests/gameCatalog.test.ts` 驗證。

### 3.2 共用版面元件

- `GameShell.tsx`：固定高度頁面、返回鍵、標題、副標、狀態與次要操作。
- `SplitChoiceLayout.tsx`：題目與選項分區。
- `CognitiveChoiceScreen.tsx`：認知選擇題的共用進度、分數與回饋結構。
- `GridFocusLayout.tsx`：網格主區、輔助側欄與不遮擋盤面的保留回饋列。
- `GridFocusScreen.tsx`：常見網格遊戲頁面的組裝層。
- `BoardSidebarLayout.tsx`：棋盤主區、狀態／操作側欄與底部保留回饋列的共用組裝層；棋盤不捲動，側欄可局部捲動。

### 3.3 固定驗收規則

- 文件本身不得在手機橫向產生水平或垂直溢位。
- 主遊戲區使用剩餘高度；只有清單、紀錄或說明區可以局部捲動。
- 可操作控制至少 44 × 44 px，相鄰主要操作保留間距。
- 一般內文以 16 px 為目標，輔助標示不得小於 12 px。
- 選取、正確、錯誤不能只依賴顏色，須搭配文字、圖示、外框或形狀。
- 重要回饋使用保留列，不可覆蓋主要盤面。
- Modal 限制最大高度並允許內部捲動。
- 動畫應尊重 `prefers-reduced-motion`。

### 3.4 版型資料契約決策

`BOARD_TABLE` 已正式定義為第六個 layout preset，並加入 `GameLayoutPreset` 與 `GAME_LAYOUT_PRESETS` 的 canonical contract。公開 21 點維持獨立牌桌型版面，不併入 `BOARD_SIDEBAR`。四子棋 reference 已通過 reviewer gate；五子棋已使用相同 `BoardSidebarLayout` 完成第二款遷移，並完成交叉點棋盤幾何、星位、外框留白與省略重複 feedback 的 visual acceptance；黑白棋完成第三款遷移並驗證 8×8 cell-based 棋盤與合法步提示；數獨完成第四款遷移，驗證 4×4／9×9 cell-based 資料輸入棋盤；點格棋完成第五款遷移，驗證 5×5 dots／4×4 boxes 的 edge-based 操作模型；其餘 BOARD 遊戲尚未開始 migration。

## 7. 建議執行節奏

1. 每批限制為 1–2 款相近遊戲。
2. 先讀本計劃書、`CODEX_HANDOFF.md`、共用版型及該批遊戲檔案，不重讀整個專案。
3. 先寫最小契約測試，證明遊戲採用正確版型、區域標籤與關鍵狀態。
4. 只遷移呈現層；若碰到規則問題，先建立可否證測試並另行處理。
5. 執行目標測試與正式版建置。
6. 在一般與進階模式實際完成一次主要操作，檢查作答前後畫面。
7. 通過後才更新進度表與 `CODEX_HANDOFF.md`。
8. 每完成一個版型階段，安排一次 Sol 複核與全套回歸。

## 8. Definition of Ready

開始每一批前必須確認：

- 遊戲規則與一般／進階差異可由現有程式或說明確認。
- 已找到主要元件、資料來源與狀態流程。
- 已決定沿用或擴充哪個共用版型。
- 不會在未授權情況下改變規則、計分或題庫。
- 已定義可自動測試與可視化驗證的完成條件。

## 9. Definition of Done

每款遊戲至少必須符合：

- 使用對應共用版型，或有記錄清楚的合理例外。
- 返回、規則、重設與主要操作符合觸控尺寸。
- 題目、盤面、選項與回饋不互相遮擋。
- 一般與進階模式皆可進入並完成主要流程。
- 最低尺寸沒有文件層級溢位或操作控制超界。
- 新增契約測試通過，既有測試無回歸。
- 正式版建置成功。
- 進度文件與交接文件同步更新。

## 11. Sol 與 Luna Max 的分工評估材料

依官方 OpenAI 文件，GPT-5.6 Sol 是複雜專業工作的旗艦模型；GPT-5.6 Luna 則針對成本敏感、高量工作最佳化。兩者皆支援 `max` 推理，但 `max` 應保留給真正困難、品質優先的工作，並以代表性工作比較品質、延遲與成本，而不是假設較高推理必然更划算。

官方資料：

- [GPT-5.6 模型使用與選擇指南](https://developers.openai.com/api/docs/guides/latest-model)
- [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)
- [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

注意：官方頁面上的 API 單價只能說明相對成本定位，不等同於 Codex 桌面版或 ChatGPT 方案中的 token 額度扣除方式；實際可用額度與模型供應仍以帳號介面為準。

## 14. 建議決策

目前最穩健的方案仍是「混合分工」，不是立即把全部剩餘 29 款一次交給 Luna Max：

1. Luna Max 已完成 `GRID_FOCUS` 試點與最後一款金字塔接龍。
2. 使用現有測試、雙尺寸實測與人工差異檢查衡量品質。
